## Root causes found
1. **>=383 / >=600 draws TRANSLATION_FAULT (v11)**: not the geometry buffer. mali_frame_build rewrote the tiler heap descriptor (BO page at geo_va) every frame with first-chunk pointers; once firmware had grown the heap (frame needing more than the initial chunks) the next frame used a descriptor inconsistent with the heap and faulted (garbage fault VA 0x106...). Descriptor now written once at queue creation (c66eb3e). drawcalls:1000 passes.
2. **Poco/CMF 'no pixels'**: 4 MiB geometry buffer (489ee83) breaks BOTH v11 and v13 (coverage 0). 64 KiB works on both (PanVK value). 67e1aa0. Override: MALI_GEOM_SIZE.
3. t_vk_draw uninitialised struct: 7eaca1f.
Debug env added: MALI_RING (CS ring bytes), MALI_HEAP_CHUNK/MALI_HEAP_INIT, MALI_GEOM_SIZE.

## Regression (after fixes, CMF and Poco): t_vk_draw, t_vk_compute pass; t_vk_meta pass (CMF); t_bc_hw 12/12 on both; M14 t_vk_present on CMF 12/12 pass (see below).

## M14 present hang (1 of 3 earlier)
12 runs of t_vk_present on CMF (10 fifo, 2 mailbox, 8 s each, qrestore between): 12/12 pass, fps 104-116 fifo, 148-174 mailbox; no hang. Not reproduced; the earlier hang most likely came from the uninitialised-struct/stale-session state (7eaca1f) or a stale session (runs after another client without qrestore). Note: the guest session must be restored (qrestore) between runs or qvkpresent refuses (focus rule). During the mdbench sweep, ours segfaulted at start 5 of 9 times and the bridge lost its server 2 times when runs followed each other WITHOUT qrestore; with qrestore before each config all runs were stable. Segfault cause not investigated (startup, before the first frame; suspect leftover state in the shared session / /tmp/mdb ICD copy).

## cube gap (ours 91 fps/11.5 ms vs bridge 157 fps/6.4 ms), per-frame means from the CSV
| cost | ours ms | bridge ms |
|---|---|---|
| 1. cpu_submit (vkQueueSubmit) | 8.85 | 0.02 |
| 2. present/acquire | 2.03 | 5.34 (vsync/compositor pacing) |
| 3. fence wait | 0.49 | 0.93 |
| record | 0.17 | 0.06 |
vkQueueSubmit is synchronous in our driver (submit_cs waits for the queue counter before returning, MALI_PIPE_DBG shows 'wait rc=0 counter=N expected=N' right after every submit_cs). The 8.85 ms = CS build + GPU time of the frame (gpu_ms 5.0) + firmware round trip; making submit asynchronous (signal the fence/semaphore from the counter, wait later) is the top fix for every scene (the ~11 ms GPU floor in gpu_ms is most likely the same wait/idle-power-up effect: the timestamp pair brackets queue idle -> run).
