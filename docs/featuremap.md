## Gaps and what is not machine-readable

- **Microsoft's D3D reference pages** have no machine-readable registry, so D3D requirements are taken from the layers that consume them (DXVK, vkd3d-proton, wined3d), pinned by revision above. A D3D-level row that no consumer source states is not in this chart.
- **The Vulkan spec prose** (semantics, valid usage) is not parsed: rows carry the registry entry and the consumer's line, not the spec paragraph.
- **Our own hardware classes** (`annotations.json`) are judgements from `M/notes/`, not machine facts; each names the note. Rows with no note print `unknown`.
- **deqp ids are struct-level**, not per member: `dEQP-VK.api.info.get_physical_device_properties2.features.vulkan12_features` PASS says our 1.2 struct was accepted, not that every member is implemented. Per-feature behaviour still needs the `vk/tests/` case in the same row.
- **dEQP has no case per feature in every group** (a LIKE search for one requirement matched 5 687 unrelated `texel` cases), so no id is attached when the exact name is absent.
- **What our phones actually report** comes from the last `bin/smoke` caps dump; a stale dump gives stale `ours` values (the file mtime is in the header line above).

No row was dropped and every row has a test this run.

**Data bug found by this generator:** in the *Device Extensions* section of `phones/x8/caps-driver.txt` 57 of 128 lines carry no extension name, `phones/cmf/caps-driver.txt` 57 of 128 lines carry no extension name. A row that reports an extension absent is therefore only certain for the named lines; the nameless ones cannot be read as present or absent. Extension rows print `?` only when *no* name survived. Reported for `bin/smoke`, not fixed from a host-only lane.
